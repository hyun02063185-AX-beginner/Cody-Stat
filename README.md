# 코디세이 마리너 자율 프로젝트

> 코디세이 교육생(마리너)이 직접 운영하는 세션 플랫폼 **cody-stat(출항일지)** 의 인계·운영·발전을 위한 저장소입니다.
> 코드가 아니라 **의사결정과 문서**를 관리하는 곳입니다.

## 프로젝트 개요

퍼실리테이터가 운영하던 cody-stat을 **9월 3일부터 교육생이 인계**받아, 본과정 약 1년 6개월 동안 직접 운영하고 키웁니다. 기존 서비스 유지에 그치지 않고 새 기능과 새 서비스도 우리가 기획합니다.

| 항목 | 내용 |
| --- | --- |
| 대상 서비스 | cody-stat — 세션 개설·참가·캘린더 구독·통계 |
| 현재 상태 | 일시 중단, 9월 3일 재시작 |
| 인계 개시 | 2026년 9월 3일 |
| 재단·퍼실리테이터 | 미관여 — 예산·장비·기술 멘토링 없음 |
| 인원 | 약 10명 |
| 개발 방식 | 바이브코딩 적극 활용 |

서비스 규모가 크지 않아 인계 부담은 적습니다. 그래서 **개발력보다 기획력이 더 중요한 프로젝트**로 보고 있습니다.

### 왜 하는가

이 프로젝트에는 서비스 운영 외에 하나의 목적이 더 있습니다. 교육생 중 SW 전공자와 비전공자가 섞여 있고, 낮에 상주하는 사람과 저녁·주말에만 오는 사람이 나뉩니다. 플랫폼은 이들이 **서로 가르치고 배우는 접점**을 만드는 도구입니다.

- 세션을 여는 사람을 늘리는 것이 기능을 늘리는 것보다 우선입니다
- 비전공자가 "배우는 쪽"에만 머물지 않도록, 자기 도메인 지식을 나눌 자리를 만듭니다
- 낮에 못 오는 사람이 따라잡을 수 있게 기록을 남깁니다

## 팀 구성 (10명)

| 팀 | 인원 | 담당 | 적합한 사람 |
| --- | --- | --- | --- |
| PO · 총괄 | 1 | 우선순위 결정, 대외 창구, 일정 관리 | 운영 경험자 |
| 기술 오너 | 2 | 코드베이스, 계정·인프라, 배포 승인, 장애 대응 | 전공자 필수 |
| 프로덕트 기획 | 3 | 인터뷰, 요구사항 정의, 화면 설계, 백로그 | 비전공자 강점 |
| 구현 | 2 | 기능 개발, 리뷰 후 배포 | 전공·비전공 혼합 |
| 운영 · 커뮤니티 | 2 | 세션 시딩, 아카이브, 공지, 문의 대응 | 저녁·주말 인원 |

### 운영 원칙

1. **모든 역할은 2인 1조** — 혼자만 아는 일을 만들지 않습니다
2. **주 역할 하나, 보조 역할 하나** — 10명으로 전 영역을 덮으려면 겸직이 기본
3. **시간대에 맞는 일** — 낮 인원은 즉시 대응, 저녁·주말 인원은 비동기 업무
4. **3개월마다 로테이션** — 기술 오너는 예외 (맥락 손실 비용이 큼)

## 직군 지도

일반적인 서비스 조직의 직군을 우리 5개 팀이 어떻게 나눠 맡는지 정리했습니다. 로테이션 때 "다음에 어떤 역할을 해볼까"를 고를 때 참고하세요.

### PO · 총괄

**흡수 직군** — PO / PM / PMO / 재무·비용 관리

- 무엇을 만들지 결정하고 우선순위를 정합니다
- 일정·리스크를 관리하고 팀 간 조율을 합니다
- 퍼실리테이터·재단·타 기수와의 대외 창구입니다
- 인프라 비용을 관리합니다

### 기술 오너

**흡수 직군** — 테크리드 / 아키텍트 / DevOps / SRE / 인프라 / DBA / 보안

- 코드베이스 구조를 파악하고 문서화합니다
- 계정·도메인·배포 환경을 관리합니다 (최소 2인 공동 관리)
- 프로덕션 배포를 승인하고, 문제 시 되돌립니다
- 인증·데이터 스키마 변경을 검토합니다
- 백업이 실제로 돌고 있는지 확인합니다

### 프로덕트 기획

**흡수 직군** — 서비스 기획 / BA / UX 리서처 / UX·UI 디자이너 / 데이터 분석가

- 세션 개설자·참가자를 인터뷰해 진짜 문제를 찾습니다
- 요구사항을 정의하고 화면을 설계합니다
- 백로그를 관리하고 우선순위 근거를 만듭니다
- 참여 지표를 정의하고 읽습니다
- 담당을 나눕니다 — 세션 / 아카이브 / 지표

### 구현

**흡수 직군** — 프론트엔드 / 백엔드 / AI 엔지니어 / QA

- 기능을 개발하고 수정합니다 (바이브코딩 중심)
- 기술 오너 리뷰를 거쳐 배포합니다
- 배포 전 직접 테스트하고 결과를 남깁니다
- 구현 과정을 세션으로 공개합니다

### 운영 · 커뮤니티

**흡수 직군** — 서비스 운영 / CS / 커뮤니티 매니저 / 테크니컬 라이터 / 콘텐츠

- 세션 개설을 독려하고 초기 콘텐츠를 채웁니다
- 끝난 세션의 자료와 요약을 정리합니다
- 공지를 쓰고 문의에 답합니다
- 신규 기수를 온보딩합니다

### 담당을 정해둬야 할 두 자리

소규모 팀에서 늘 빠지는 자리입니다. 전담자가 아니어도 **이름만은 정해두세요.**

- **QA** — 바이브코딩으로 개발 속도가 빨라지면 검증이 병목이 됩니다 (구현팀 겸임 권장)
- **개인정보 보호 담당** — 디스코드 로그인 정보를 다루는데 재단과 무관한 자체 운영입니다 (기술 오너 겸임 권장)

## GitHub Pages 설정

1. 저장소 **Settings** → 왼쪽 메뉴 **Pages**
2. Source를 **Deploy from a branch**로 선택
3. Branch를 `main` / 폴더를 `/ (root)`로 지정하고 저장
4. 몇 분 뒤 `https://<계정명>.github.io/<저장소명>/` 에서 `index.html`이 열립니다

저장소를 Public으로 두면 로그인 없이 누구나 볼 수 있습니다. Private 저장소에서 Pages를 쓰려면 유료 플랜이 필요하니, 공개 자료만 올린다는 전제로 Public을 권합니다.
