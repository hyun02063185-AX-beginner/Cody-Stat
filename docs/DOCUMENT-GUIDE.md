# 문서 체계 가이드

이 저장소의 문서를 **누가, 언제, 어떻게** 쓰는지 정합니다.
1년 6개월 동안 사람이 바뀝니다. 문서는 그 사이를 잇는 유일한 수단입니다.

---

## 세 가지 원칙

**하나 — 문서마다 담당이 한 명입니다.**
"팀이 관리"는 아무도 관리하지 않는다는 뜻입니다. 각 문서 맨 위에 담당자 이름을 적습니다.

**둘 — 결정은 반드시 남깁니다.**
6개월 뒤 "이거 왜 이렇게 정했지"가 반드시 나옵니다. 결과만이 아니라 **배경과 탈락한 대안**까지 적습니다.

**셋 — 문서가 코드보다 오래 삽니다.**
바이브코딩으로 만든 코드는 언제든 다시 만들 수 있습니다. 하지만 "왜 그렇게 만들었는지"는 못 만듭니다.

---

## 문서별 상세

### `00-decisions/decision-log.md` — 담당: PO

모든 결정을 한 줄씩 시간순으로 쌓습니다. 이 저장소에서 **가장 중요한 문서**입니다.

```
| 날짜 | 결정 | 배경 | 결정자 |
| 2026-09-05 | 9월 중 기능 추가 없이 인계에만 집중 | 코드 파악이 우선 | 전체 합의 |
```

작성 기준 — 되돌리기 어려운 것, 돈이 드는 것, 여러 사람에게 영향이 가는 것.

### `00-decisions/adr/` — 담당: 결정을 주도한 팀

큰 결정은 한 줄로 부족합니다. `YYYY-MM-DD-제목.md` 형식으로 파일을 만들고 아래를 채웁니다.

- **배경** — 어떤 상황에서 결정이 필요했나
- **선택지** — 어떤 안들을 검토했나
- **결정** — 무엇을 골랐나
- **이유** — 왜 그것인가
- **버린 것** — 다른 안을 왜 안 골랐나 (이게 가장 값집니다)

### `01-handover/` — 담당: 기술 오너

9월 인계 기간에 집중적으로 씁니다. 이후에는 거의 건드리지 않는 기록물입니다.

- `checklist.md` — 넘겨받을 것 목록과 완료 여부
- `accounts.md` — 어떤 계정이 있고 누가 접근 권한을 갖는지. **비밀번호·토큰은 절대 적지 않습니다**
- `qna.md` — 원작자에게 물어본 것과 답변. 원작자를 다시 만나기 어려우니 그날 최대한 받아 적습니다

### `02-product/backlog.md` — 담당: 프로덕트 기획

만들 것 목록입니다. 주 1회 정리합니다.

| 항목 | 왜 필요한가 | 근거 | 우선순위 | 상태 |

"근거"에 인터뷰 기록 링크를 답니다. 근거 없는 항목은 **누군가의 취향**입니다.

### `02-product/research/` — 담당: 프로덕트 기획

인터뷰마다 파일 하나. `YYYY-MM-DD-누구.md`

들은 말을 **요약하지 말고 그대로** 적습니다. 해석은 나중에 바뀌지만 발언은 안 바뀝니다.

### `02-product/specs/` — 담당: 프로덕트 기획

기능 착수 전에 씁니다. 화면 스케치는 손그림 사진도 괜찮습니다.

- 무엇을 해결하는가 / 사용자가 하는 일 / 화면 / 예외 상황 / 완료 기준

### `03-tech/architecture.md` · `data-model.md` — 담당: 기술 오너

인계 직후 가장 먼저 쓸 문서입니다. 코드를 읽으면서 정리하는 게 파악에도 빠릅니다.

### `03-tech/deploy.md` — 담당: 기술 오너

배포 방법과 **되돌리는 방법**. 되돌리기가 더 중요합니다.

### `03-tech/runbook.md` — 담당: 기술 오너

문제가 생겼을 때 순서대로 뭘 해보는지. 새벽에 당황한 사람이 그대로 따라 할 수 있게 씁니다.

### `04-ops/policy.md` — 담당: 운영·커뮤니티

세션 개설 규칙, 장소 예약 절차, 게시물 기준. 지하 1층 대관처럼 퍼실리테이터 확인이 필요한 절차도 여기 적습니다.

### `04-ops/privacy.md` — 담당: 개인정보 담당

수집 항목, 이유, 보관 기간, 삭제 절차, 접근 권한자.
재단과 무관한 자체 운영이라 **책임 소재를 문서로 남겨두는 것이 안전합니다.**

### `04-ops/release-notes.md` — 담당: 구현

배포할 때마다 한 줄. 사용자가 읽는 말로 씁니다.
❌ "세션 API 리팩터링" → ✅ "세션 목록이 빠르게 열립니다"

### `05-metrics/metrics.md` — 담당: 프로덕트 기획

월 1회 기록합니다. 우리가 보는 것:

- 세션 개설 수 / 개설자 수 (같은 사람이 반복인지 확인)
- 참가 인원
- 비SW 세션 비중
- 저녁·주말 세션 비중
- 신규 개설자 수 ← **가장 중요**. 이 숫자가 0이면 커뮤니티가 닫히는 중입니다

### `06-team/roster.md` · `rotation.md` — 담당: PO

지금 누가 무슨 역할인지, 지금까지 누가 어떤 역할을 거쳤는지.

### `06-team/onboarding.md` — 담당: 운영·커뮤니티

새로 합류한 사람이 첫날 읽는 문서. **읽는 순서**를 정해주는 것이 핵심입니다.

## 문서 작성 규칙

- **제목 아래 첫 줄에 담당자와 최종 갱신일**을 적습니다
- 링크는 파일 경로로 겁니다 (`[백로그](../02-product/backlog.md)`)
- 확정되지 않은 내용은 `(초안)` 또는 `TBD`로 표시합니다
- 잘못된 내용을 발견하면 담당이 아니어도 고칩니다. 고치고 담당에게 알립니다
- **비밀값(토큰, 비밀번호, API 키)은 어떤 문서에도 적지 않습니다**

## 로테이션 때 하는 일

3개월마다 역할이 바뀝니다. 넘길 때 다음을 합니다.

1. 담당 문서를 최신 상태로 갱신
2. 문서 맨 위 담당자 이름 변경
3. 인계 대화를 `06-team/rotation.md`에 한 단락으로 기록
4. 계정 권한이 있다면 새 담당에게 추가 (기존 권한은 바로 회수하지 말고 2주 유예)

문서가 최신이면 인계는 30분이면 끝납니다. 아니면 며칠이 걸립니다. 그 차이가 이 가이드가 존재하는 이유입니다.
